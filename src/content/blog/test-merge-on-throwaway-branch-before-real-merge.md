## 場景

手上有一個 feature 分支，開發了一段時間沒回頭同步主幹。某天要準備收尾，發現主幹跟這個 feature 分支已經分岔了好一陣子——主幹領先了一百多個 commit，feature 分支自己也累積了三十幾個 commit，兩邊都在動。

這時候心裡通常會冒出兩個問題：

1. 這個合併會有多痛？值不值得現在就做，還是再拖一下？
2. 真正的衝突會出現在哪裡？

這篇文章記錄的不是什麼複雜技巧，而是一個很簡單、但常常被跳過的習慣：**在真正合併之前，先在一個拋棄式分支上實際跑一次合併，看結果，再決定怎麼做**。跟用猜的（翻 diff、腦內模擬）比起來，跑一次真正的 `git merge` 便宜太多，而且結果不會騙人。

（背景：這次是我跟一個 AI coding agent 協作跑完整個流程的，過程中它在正式動手前先做了這次排練，我覺得這個順序本身值得寫下來，跟工具無關，手動操作一樣適用。）

## 為什麼不直接合併就好

直接合併當然可以，`git merge` 遇到衝突會停下來，你再一個個處理。問題是「先合併再看」有兩個成本：

- **合併是有狀態的操作**。一旦開始，工作目錄就進入合併中的狀態，中途想先去做別的事、或發現不想合了要收手，都要多繞一手（`git merge --abort`、或處理一半的暫存區）。
- **看不到全貌**。你可以用 `git diff --stat` 分別看兩條分支各自改了哪些檔案，用兩份檔案清單取交集（`comm -12` 配合排序過的檔名清單）抓出「兩邊都動過的檔案」，藉此**推測**衝突可能出現在哪。但這終究是推測——Git 的合併演算法看的是逐行的變更範圍，不是「這個檔案被動過」這麼粗的粒度。同一個檔案兩邊都改了，很常見的結果是自動合併成功（改的是檔案裡不同的區塊），比用猜的更常見的是「以為會衝突的檔案沒事，沒想到的地方反而衝突」。

與其花時間盯著 diff 猜，不如把這個「猜」的動作換成一次真正、但完全可以丟掉的合併。

## 排練的做法

核心想法很單純：**在一個從 feature 分支切出來的暫存分支上跑合併，看完結果就整個丟掉，完全不影響真正的分支。**

```bash
# 1. 確認工作目錄乾淨，記下目前在哪個分支
git status
git branch --show-current   # feature/big-feature

# 2. 從目前分支切一個明確標示「用完就丟」的暫存分支
git branch -f _merge-test-scratch feature/big-feature
git checkout _merge-test-scratch

# 3. 在這個暫存分支上跑合併，但先不要真的產生 commit
git merge origin/main --no-commit --no-ff

# 4. 看衝突出現在哪些檔案、衝突內容是什麼
git status --short
grep -rn '^<<<<<<<\|^=======\|^>>>>>>>' <衝突檔案>

# 5. 看完就直接丟掉，不做任何清理以外的事
git merge --abort
git checkout feature/big-feature
git branch -D _merge-test-scratch
```

幾個容易漏掉、但實際跑起來一定會踩到的細節：

**工作目錄如果有未commit的修改，合併會直接被擋下來。** 如果那個修改是「這個分支上一直保留、還不打算真的 commit」的東西（例如本地的設定檔調整），先用 `git stash push -- <檔案>` 把它單獨存起來，跑完排練、清乾淨暫存分支之後，記得要 `git stash pop` 或 `git stash drop` 做個了結——不要留著一筆不明用途的 stash 過夜，之後自己都會忘記它是幹嘛的。

**`--no-commit --no-ff` 這個組合是關鍵。** `--no-ff` 確保就算沒有真正的衝突（例如剛好是 fast-forward 的情況）也會照樣走一次真正的三方合併邏輯，不會因為「其實不需要合併」而讓這次排練失去意義；`--no-commit` 讓你在合併結果產生之後、變成一個 commit 之前，有機會先檢查，滿意再繼續，不滿意直接 abort。

**排練完的乾淨收尾，跟排練本身一樣重要。** `git merge --abort` 只在合併還沒 commit 時有效，這也是為什麼要搭配 `--no-commit`。收尾之後那個暫存分支就完全沒有存在的意義了，直接刪掉，不要留著——留著只會在下次 `git branch` 列分支時多一個要解釋「這是什麼」的東西。

## 排練帶回來的資訊，怎麼用

跑完一次真正的合併（就算是丟棄的），你會拿到兩種在猜測階段拿不到的東西：

**確切的衝突檔案清單，而且通常比你以為的少。** 用兩份 diff 檔名清單取交集算出來的「兩邊都動過的檔案」，只是「可能衝突」的上限；實際跑完合併，常見的結果是這個清單裡有一半以上其實自動合併成功了，真正需要人工看的只有一小部分。與其一開始就對著一份誇大的風險清單緊張，不如先跑一次拿到真實數字。

**每個真衝突的實際內容，讓你能判斷這是「良性衝突」還是「邏輯衝突」。** 這個區分很重要，決定了合併之後還要不要做額外的驗證：

- *良性衝突*：兩邊在檔案的同一個位置，各自新增了互不相關的內容（例如一份設定檔的選項清單，兩邊都各自加了一行新選項；或一份只會被拿去執行插入的資料腳本，兩邊都各自加了一段獨立的 insert）。這種衝突的正確處理方式幾乎都是「兩邊都留著」，串接起來即可，風險很低。
- *邏輯衝突*：兩邊改的是同一段邏輯本身，例如同一個函式被兩邊用不同方式重寫。這種衝突光是解掉語法上的 `<<<<<<<` `=======` `>>>>>>>` 標記不夠，還要理解兩邊的意圖，決定合併後的正確行為是什麼，通常合併完要額外補測試或手動驗證。

排練階段看到的衝突，如果全部都是良性的，就代表這次合併雖然「規模大」（commit 數字嚇人），但「風險低」——可以放心正式合併，合併完跑一次編譯/測試確認沒有殘留問題就好，不需要如臨大敵。反過來，如果排練階段就發現是邏輯衝突，那至少你在正式動手之前就知道要留多少時間、要找誰確認邏輯該怎麼寫，而不是合併到一半才發現。

## 小結

這個習慣沒有任何新技術，`git merge --no-commit --no-ff` 加上一個用完就刪的分支，是每個用 Git 的人都會的操作組合。它真正的價值在於**把「合併會不會很痛」從一個靠經驗猜測的問題，變成一個幾秒鐘就能拿到確定答案的問題**——尤其是在分岔已經拖了很久、兩條分支都各自活躍開發的情況下，猜測的準確度會隨著分岔時間拉長而快速下降，而排練的成本幾乎不會變。

下次遇到「這兩條分支已經分岔很久了，合併會很痛嗎」這種問題時，與其站在那裡瞪著 `git log --graph`，不如花十秒鐘切一個暫存分支，直接跑一次看看。
